# Brief P0-T3: MoveIt2 on the MuJoCo simulation

Effort: medium
Type: config. No file changes are planned. Daniel runs the launch and the RViz check; Opus
reads the logs and records the result. If the launch fails and a fix inside a `franka_*` package
is needed, Opus proposes it and Daniel decides before anything is edited.

## Goal
Show that the repo's existing `franka_moveit_config/launch/sim_moveit.launch.py` starts
`move_group` without plugin errors, and that a motion planned in RViz is executed by the MuJoCo
Panda. Phase 2 (P2-T2) derives `probe_sim_moveit.launch.py` from this file, so we need to know
whether it works as it is and what its weak points are.

The packages this task was first about (`moveit_simple_controller_manager`,
`joint_trajectory_controller`) were already installed during P0-T2.

## What was checked on 2026-11-21 (before writing this brief)

### Safety: can this launch reach the real robot?
No. Everything it starts runs on this PC and talks only to MuJoCo:
- `sim_moveit.launch.py` includes exactly one other launch file,
  `franka_bringup/launch/sim/launch_mujoco_ros_server.launch`. Nothing under `launch/real` or
  `launch/mixed` is included.
- The hardware plugin comes from the URDF: `robots/sim/panda_arm_sim.urdf.xacro` includes
  `robots/sim/panda_arm_sim.ros2_control.xacro`, which sets
  `<plugin>franka_hardware/FrankaMjHardwareSystem</plugin>`. Its source
  (`franka_hardware/src/sim/`) reads and writes MuJoCo's `mjData`. It uses libfranka only for
  data types (`franka::RobotState`, `franka::GripperState`, `franka/exception.h`); it has no
  robot IP parameter and opens no connection.
- No node gets a `robot_ip` parameter. The real hardware plugin (`franka_hardware/FrankaHardwareInterface`)
  is not referenced.
- The only `ros2 run` it executes is `controller_manager spawner` for `panda_arm_controller` and
  `joint_state_broadcaster`, aimed at the default `/controller_manager`, which in this launch is the
  one inside the MuJoCo node.
- The installed copy under `~/ros2_ws_3/install/franka_moveit_config/share/` is identical to the source.

One remaining path, outside the launch file: ROS 2 nodes discover each other over the network.
`ROS_DOMAIN_ID` and `ROS_LOCALHOST_ONLY` are not set in `~/start_env.sh` or `~/.bashrc`, and the
PC's wired interface is up. If another machine on the same network ran a real Panda stack on
domain 0, both would have a node called `/controller_manager` and topics could mix. To rule this
out, the commands below set `ROS_LOCALHOST_ONLY=1` in each terminal (not permanently).

### What each node does
| Started by | Node | Purpose |
|---|---|---|
| included `.launch` | `mujoco_server` (`mujoco_ros/mujoco_node`) | Runs the MuJoCo physics and viewer with `mujoco/franka/scene.xml` (arm plus hand). Publishes sim time on `/clock`. Loads the `mujoco_ros2_control` plugin, which starts a `controller_manager` with `FrankaMjHardwareSystem` and, because `hand` is true, a gripper action server node `panda_gripper_sim_node`. |
| launch file | `move_group` | MoveIt2: plans with OMPL, solves IK with KDL, checks collisions, and sends planned trajectories to `/panda_arm_controller/follow_joint_trajectory`. |
| launch file | `rviz2` | GUI with the MotionPlanning panel (`rviz/moveit.rviz`); you set goals and press Plan / Execute here. |
| launch file | `robot_state_publisher` | Publishes tf from `/joint_states` and holds `robot_description` (also read by the MuJoCo plugin and by Slicer). |
| launch file | `joint_state_publisher` | Merges `/joint_states` and `/panda_gripper_sim_node/joint_states` into `/joint_states` at 30 Hz. |
| `ExecuteProcess` | `spawner panda_arm_controller` | Loads and activates the `JointTrajectoryController` (effort interface, PD gains per joint) from `config/sim_panda_ros_controllers.yaml`. This is what moves the arm. |
| `ExecuteProcess` | `spawner joint_state_broadcaster` | Publishes the simulated joint positions on `/joint_states`. |
| launch file, only if `db:=true` | `mongo_wrapper_ros.py` | Warehouse database. Off by default, and `warehouse_ros_mongo` is not installed, so leave `db` false. |

Compared with `franka_sim.launch.py`, this launch does **not** start rosbridge, `tf2_publisher`
or the `cartesian_impedance_controller`. The two launches must not run at the same time: each
starts its own MuJoCo.

### Installed packages
`moveit_ros_move_group`, `moveit_ros_visualization`, `moveit_planners_ompl`, `moveit_kinematics`,
`moveit_simple_controller_manager` (all 2.5.10), `joint_trajectory_controller`, `rviz2`,
`joint_state_publisher` are installed (`dpkg -l`).

### Problems expected from reading the files (verify)
1. **Gripper controller name mismatch.** `config/panda_controllers.yaml` tells MoveIt to use
   `panda_gripper/gripper_action`, but the sim gripper server is `panda_gripper_sim_node`, so its
   action is `/panda_gripper_sim_node/gripper_action`. Expected: a warning that the
   `panda_gripper` action server is not available; planning for the `hand` group cannot execute.
   The arm is not affected, and the probe replaces the gripper later. Not fixed in this task.
2. **Sim time vs wall time.** The MuJoCo node and its `controller_manager` use sim time (the
   plugin forces `use_sim_time` true, `mujoco_ros2_control.cpp:283`). `move_group`, `rviz2`,
   `robot_state_publisher` and `joint_state_publisher` get no `use_sim_time`, so they use wall
   time. `move_group` may then report that it "didn't receive robot state with recent timestamp",
   or execution may time out. Unclear in advance, because `joint_state_publisher` re-stamps
   `/joint_states` with wall time.
3. `FrankaMjHardwareSystem` reads `hand_1` as the string `"True"`; the xacro passes `true`. The
   P0-T4 run showed gripper state in tf, so this probably works; check the log for
   "Gripper found for panda".

SRDF named states (`srdf/group_definition.xacro`): `ready` is
`0, -pi/4, 0, -3pi/4, 0, pi/2, pi/4`, the same as the launch's start pose, so planning to `ready`
from the start does nothing. `extended` is `0, 0, 0, -0.1, 0, pi/2, pi/4` (arm almost straight up),
a large but visible test motion.

Not checked: whether `move_group` actually starts cleanly, and whether the arm follows the
trajectory closely enough for MoveIt's tolerances (`allowed_start_tolerance` 0.01 rad, goal margin 0.5 s).

## Progress
### First run (2026-11-21)
Daniel ran step 1. MuJoCo and RViz opened, but RViz showed no robot.
- **Good:** `move_group` printed "You can start planning now!" with no plugin-not-found error.
  Both spawners activated their controllers. The log contained "Gripper found for panda", so
  expected problem 3 did not occur.
- **Cause of the missing robot:** RViz's MotionPlanning display failed to load the robot model,
  twice: `parameter 'panda_arm.kinematics_solver_timeout' has invalid type ... double ... string`.
- **Why:** the launch file passes `kinematics.yaml` at the top level, so the parameters become
  `panda_arm.kinematics_solver...`. MoveIt 2.5.10 reads them only under
  `robot_description_kinematics.<group>.` (the strings in `libmoveit_kinematics_plugin_loader.so`
  and `libmoveit_kdl_kinematics_plugin.so` show this prefix). So the top-level copies are useless
  to MoveIt, and in RViz they collide with something that sets them as strings. Which code
  does that was not found; it is not in the installed headers.
  Probably also affects `move_group`: it gets no IK solver settings, so pose goals and the RViz
  interactive marker would not work even with the display fixed (verify).
- **Proposed fix (needs Daniel's approval, `franka_*` change):** in `sim_moveit.launch.py` pass
  `{'robot_description_kinematics': kinematics_yaml}` instead of `kinematics_yaml` to both
  `move_group` and `rviz2`. This is the layout MoveIt's own `moveit_configs_utils` uses.
- **Fix applied** (Daniel approved, 2026-11-21): `sim_moveit.launch.py` now builds
  `robot_description_kinematics = {'robot_description_kinematics': kinematics_yaml}` and passes it
  to `move_group` and `rviz2`, with a comment saying why. `franka_moveit_config` rebuilt; the
  installed file matches the source. `franka_moveit_config_srdf_tests` 3 of 3 pass; `flake8` has
  30 findings in this file before and after the edit (baseline failure, nothing new). The other
  MoveIt launch files still have the old pattern (out of scope).
- **Second run (same day): the fix did not help.** RViz still shows no robot. The error is the
  same, now for `robot_description_kinematics.panda_arm.kinematics_solver_timeout`.
  `move_group` loads the kinematics without error in both runs, so only RViz fails.
  - rclcpp's message means: the parameter was declared as double, and a **string value** was
    then applied to it.
  - MoveIt Humble's `kinematics_plugin_loader.cpp` declares the timeout only as double and never
    sets it (read on GitHub, `humble` branch). It is the only installed library that contains
    the name.
  - Offline probe: the params file `launch_ros` writes for `rviz2` gives the timeout as a double
    (a throwaway rclpy node named `rviz2` loaded it as `Type.DOUBLE 0.05`).
  - So the string comes from inside RViz at run time.
- **Cause found (third run, read-only queries on the live system):** the number locale.
  - The ROS 2 daemon was stale and showed no nodes; `--no-daemon` showed all of them.
  - On `/move_group` the timeout is `double`. On `/rviz2` it is "Parameter not set": the declaration threw.
  - The four params files given to `rviz2` were copied and loaded into a probe node: the timeout is declared as double without error.
  - The RViz process has `LC_NUMERIC=hr_HR.UTF-8` (decimal comma). Qt applies the system locale
    at start, and the ROS 2 YAML parameter parser reads numbers in that locale. So `0.05` is not a
    number there and becomes the string `'0.05'`.
  - Reproduced: the same probe after `setlocale(LC_ALL, "")` with `LC_NUMERIC=hr_HR.UTF-8` fails
    with "Trying to set parameter ... to '0.05' of type 'STRING', expecting type 'DOUBLE'"; with
    `LC_NUMERIC=C` it passes.
  - `move_group` has no Qt, so it keeps the C locale and is unaffected.
  - **The kinematics prefix change was not needed.** MoveIt's loader first tries the bare group name
    (`panda_arm.kinematics_solver`), so the original file was valid. Reverted on Daniel's request
    (`git checkout`), rebuilt; `sim_moveit.launch.py` is unchanged from upstream again.
  - Fix to test: start the launch with `LC_NUMERIC=en_US.UTF-8`. Options for making it
    permanent: `~/start_env.sh` (Daniel's file), or `additional_env` on the `rviz2` node in our own
    launch file in P2-T2.
  - Other Qt programs on this PC (Slicer) start under the same locale; any double parameter they
    read from YAML could hit the same problem.
- **Also seen, harmless:** `/recognize_objects not available` (object recognition, unused);
  `No 3D sensor plugin(s) defined for octomap` (no depth camera configured).
- **Important for step 4:** MuJoCo logged "Starting Simulation in paused mode". Sim time and the
  controllers do not advance until the simulation is unpaused (Space in the MuJoCo viewer), so
  an execution started while paused would time out.
