# Brief P0-T8: explain the 2026-11-13 tf failure

Effort: medium
Type: config. Daniel starts and stops the simulation and Slicer; Opus runs read-only checks
(`ros2 node list`, `topic info/echo`, `param get`, `tf2_echo`) while they run. No code, no subagent.

## Goal
On 2026-11-13 every tf lookup in Slicer failed with "panda_link0 does not exist". Find out whether
this still happens on the current base, and if it does, why. The answer goes into
`STUDENT_GUIDE.md`, section 14, so the same symptom later is recognised at once.

## What is known (checked 2026-11-24)
- The 2026-11-13 Slicer log no longer exists. Slicer writes its log to `/tmp/Slicer-daniel/`, which
  is cleared on reboot; the files in `~/.ros/log/SlicerApp-real_*.log` (one from 2026-11-13 23:35)
  are all empty. Only the one-line note in `STUDENT_GUIDE.md` section 14 remains.
- That run used the **old** workspace `~/ros2_ws_2` and its `franka_sim.launch.py`, without RViz or
  MoveIt. That launch is a different system from today's:
  - MuJoCo ran inside `franka_control2_node` (ros2_control), with joint states remapped to
    `franka/joint_states`; no `mujoco_server`, no `/clock`, no `use_sim_time` anywhere.
  - `joint_state_publisher` merged `franka/joint_states` and `/panda_gripper_sim_node/joint_states`.
- Today's base has two ways to start the simulation:
  - `start_panda_sim` = `franka_bringup franka_sim.launch.py`: `mujoco_server` with
    `use_sim_time: true`, `robot_state_publisher` and `joint_state_publisher` without it,
    `joint_state_broadcaster`, `cartesian_impedance_controller`, rosbridge, `tf2_publisher`.
  - `franka_moveit_config sim_moveit.launch.py`: the same MuJoCo server, plus `move_group`, RViz,
    `panda_arm_controller`. Used in P0-T3 and on 2026-11-24.
- On 2026-11-24 with `sim_moveit.launch.py` + RViz + Slicer, Slicer followed the executed motion. Its
  log showed only the expected warnings (no visual for `panda_link8` and `panda_hand_tcp`, the root
  link refusing itself as parent), and no "does not exist".
- Fixed since 2026-11-13, and each a possible cause then: `ROS_LOCALHOST_ONLY` differing between
  terminals (fixed 2026-11-21), a stale ROS 2 daemon (`start_slicer` uses `--no-daemon` since
  2026-11-21), Slicer started before the simulation (`start_slicer` refuses since 2026-11-21).
- In the URDF, `panda_link0` is the root. It appears in tf only as the parent of the moving joint
  `panda_joint1`, so it exists in tf only while `robot_state_publisher` receives joint states.
  "panda_link0 does not exist" therefore means: no `/tf` (non-static) message reached Slicer.

- Added 2026-11-24: Daniel has a saved Slicer output of an old run (MuJoCo + Slicer only, robot shown
  and moving in Slicer). Each failing lookup appears exactly twice, then no more. Only lookups over
  **moving** joints failed (`link0→link1` … `link6→link7`, `hand→leftfinger`, `hand→rightfinger`);
  lookups over fixed joints (`link7→link8`, `link8→hand`, `hand→hand_tcp`) never failed.
  SlicerROS2 code: the module spins every 20 ms (`qSlicerROS2Module.cxx` line 38) and logs every
  failed lookup on every spin, with no rate limit (`vtkMRMLROS2NodeNode.cxx` lines 676–677).
  Reading: fixed joints come on the latched `/tf_static` and are there at once; moving joints come
  on `/tf` (measured 15 Hz in Run 1, so up to about 70 ms between messages), so the first few spins
  can run before the first `/tf` message. This is a startup delay, not a failure. Not known: whether that saved output is the
  2026-11-13 log (it has no time stamps).

Not checked: whether `joint_state_publisher` keeps publishing (and so `/tf` keeps coming) while
MuJoCo is paused; whether the old workspace still starts at all (its install was built against
MuJoCo 3.1.6, and `~/start_env.sh` puts 3.2.0 first).

## Results

### Run 1 (2026-11-24): sim only, new workspace — passed
- Slicer output: only the four known messages (no visual for links 8 and 12, two empty-filename
  STL reader errors, root link refused as its own parent). **No** "could not find the transform"
  line at all: this time the first `/tf` arrived before Slicer's first lookup.
- `tf2_echo panda_link0 panda_link8`: first line "frame does not exist", one second later the
  transform (x 0.307 m, z 0.590 m, the start pose). The same startup delay as in Slicer, in a plain terminal tool.
- `/tf` at 15.0 Hz (`ros2 topic hz`). `use_sim_time`: `mujoco_server` true, `robot_state_publisher`
  and `joint_state_publisher` false; `/joint_states` stamps are wall-clock time (equal to `date +%s`).
- Slicer followed the robot (Daniel): while MuJoCo was paused and joints were moved by hand in the
  viewer (Shift+Tab panel), and after resuming, when the robot moved back. So `/tf` keeps coming while
  MuJoCo is paused (answers the "not checked" point above).
- "Robot returns to home": `start_panda_sim` starts `cartesian_impedance_controller`. On activation it
  stores the current end-effector pose and joint angles as its target
  (`franka_example_controllers/src/subscriber/cartesian_impedance_controller.cpp`, `on_activate`)
  and pulls the arm back to them with a soft spring (`pos_stiff`/`rot_stiff` 10.0 in
  `franka_bringup/config/sim/single_sim_controllers.yaml`). Expected behaviour, not a fault.
- Side finding: `ros2 topic info ... --no-daemon` gave a different publisher count for `/tf` on each
  call (0, 1, 2); without the daemon it only listens briefly. Use `ros2 topic hz` or `tf2_echo` instead.

### Run 2 (2026-11-24): Slicer first, then the sim — passed, no difference to Run 1
- Run three times. Each Slicer output: the same four known messages, **no** "could not find the
  transform" line. Daniel saw no difference to Run 1.
- Checks during the third start: `/tf` at 15.0 Hz; `tf2_echo panda_link0 panda_link8` gives
  x 0.307 m, y 0.013 m, z 0.589 m (start pose, slightly moved). `ros2 node list --no-daemon` listed
  nothing that time: the same incomplete discovery without the daemon as in Run 1, not a fault.
- So start order does not matter on the current base, as long as the robot is added after the sim is up.

### Run 3 (2026-11-24): robot added before the sim — error reproduced, recovers by itself
- Robot added with no sim: `AddParameter: parameter node for /robot_state_publisher doesn't seem
  to be available` and `parameter service for /robot_state_publisher is not ready`, then
  `parameter "robot_description" is not set`. No robot shown.
- After `start_panda_sim`: Slicer kept waiting, read `robot_description` as soon as
  `robot_state_publisher` appeared, and built the robot by itself (same four known messages).
- Then the **2026-11-13 error appeared**: "could not find the transform … panda_link0 … does not
  exist", for the same 9 lookups over moving joints as in Daniel's saved log, repeated for well over
  20 rounds (each round = one 20 ms spin, so roughly half a second or more), then it stopped.
  Lookups over fixed joints never failed.
- The robot then followed MuJoCo normally (Daniel).
- Reading: here Slicer built the robot the moment `robot_state_publisher` started, while the rest of
  the sim (MuJoCo, controllers, `joint_state_broadcaster`) was still coming up, so moving-joint
  `/tf` started later than in Runs 1 and 2. The longer the gap between "robot added" and "first
  `/tf`", the more rounds of the error. It is the same startup delay, just longer.

### Run 4 (2026-11-24): old workspace `~/ros2_ws_2`, sim first — no error
- MuJoCo started from the old install (`ros2_ws_2/install/franka_control2/.../franka_control2_node`
  running, MuJoCo inside it; no `/clock` topic). Nothing in `~/ros2_ws_2` was built or changed.
- Slicer output: the same four known messages, **no** "could not find the transform" line.
- Checks (old environment): `/tf` at 15.0 Hz; `robot_state_publisher` `use_sim_time` false;
  `tf2_echo panda_link0 panda_link8` gives x 0.359 m, z 0.643 m (the old base's start pose differs
  from the new one's).
- Not tested: whether Slicer follows motion. The old launch loads no arm controller (only
  `joint_state_broadcaster` among the nodes), and its viewer has no joint panel, so nothing can
  move the arm without loading a controller. Not needed: following was shown in Runs 1 to 3.
- So the old base itself shows no error when the robot is added after the sim is up. The error is
  not tied to the old base; it depends only on when the robot is added (Run 3).

### Run 5 (2026-11-24): MoveIt sim, Slicer first, robot added before the sim — like Run 3
- Daniel started Slicer, added the robot, then started `sim_moveit.launch.py`, moved the robot in
  MuJoCo and executed a MoveIt motion from RViz.
- Slicer output: `/robot_state_publisher` not available, `robot_description` "is not set" (three
  times, Slicer retrying), then the robot was built by itself, then the same 9 "could not find the
  transform" lines over moving joints for many rounds. Lookups over fixed joints never failed.
- Checks afterwards (everything still running): `/tf` at 14.5 Hz; `tf2_echo panda_link0 panda_link8`
  gives x -0.284 m, y -0.116 m, z 0.590 m, i.e. the arm had moved away from the start pose
  (x 0.307 m), so the executed motion reached tf.
- Daniel confirmed: the lines stopped shortly after the robot had fully loaded, and Slicer followed
  both the MuJoCo drag and the MoveIt execution.
- Same pattern as Run 3: the robot was added before the sim, so the error lasts until the moving
  joints publish.

### Conclusion
"panda_link0 does not exist" (and the same for links 1 to 6 and the fingers) is not a failure. It
means Slicer already has the robot model but has not yet received a `/tf` message for the moving
joints. It appears for a few rounds when the robot is added to a running sim, and for longer
(about half a second or more) when the robot is added before or while the sim starts. It stops by
itself; afterwards Slicer follows the robot. Neither the launch file (sim only, MoveIt), the start
order, sim time, nor the old base changes this. Only a message that keeps repeating would be a real
problem (then check that the sim is running and `ros2 topic hz /tf`).
