## Steps

### 1. MuJoCo 3.2.0 into its own folder
Same recipe as the 3.1.6 build, with two changes:
- `-DCMAKE_INSTALL_PREFIX` sends the install to `~/Libraries/mujoco-3.2.0` instead of the default
  `/usr/local`, so 3.1.6 is not overwritten.
- `cmake --install .` instead of `sudo make install`. `/usr/local` belongs to root, which is why
  the old install needed sudo. A folder in Daniel's home belongs to him, so no sudo is needed.

The configure step downloads MuJoCo's third-party libraries. About 1 to 2 GB of disk, 10 to 20 minutes.
```bash
cd ~/za_libfranku
git clone https://github.com/google-deepmind/mujoco.git mujoco-3.2.0
cd mujoco-3.2.0
git checkout 3.2.0
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=$HOME/Libraries/mujoco-3.2.0 ..
cmake --build . -- -j4
cmake --install .
```
As with 3.1.6, this also builds and installs `simulate`, MuJoCo's own viewer program
(`~/Libraries/mujoco-3.2.0/bin/simulate`). Nothing else uses it; it is handy for opening a model by hand.

Check: `ls ~/Libraries/mujoco-3.2.0/lib/cmake/mujoco` lists `mujocoConfig.cmake`, and
`ls /usr/local/lib/libmujoco.so.*` still shows only 3.1.6.

### 2. Point `~/.bashrc` at MuJoCo 3.2.0
Replace lines 121-122 of `~/.bashrc` with the block below (it also removes the duplicate entries).
Daniel edits the file, or Claude does it with his OK at that time.
```bash
# MuJoCo 3.2.0 (own folder) comes first, so CMake and the loader find it before 3.1.6 in /usr/local.
export MUJOCO_DIR="$HOME/Libraries/mujoco-3.2.0"
export CMAKE_PREFIX_PATH="$MUJOCO_DIR:/opt/eigen-3.3.9/:/usr/local/lib/cmake/:$CMAKE_PREFIX_PATH"
export LD_LIBRARY_PATH="$MUJOCO_DIR/lib:/usr/local/lib/:$LD_LIBRARY_PATH"
export LIBRARY_PATH="$MUJOCO_DIR/lib:$LIBRARY_PATH"
```
Then open a new terminal (or `source ~/.bashrc`) before the next steps.

Effect on the old workspace: it still runs, because its programs ask for `libmujoco.so.3.1.6` by
name and that file stays in `/usr/local/lib`. Rebuilding it would pick up 3.2.0 and may fail.
Accepted: the new workspace becomes the main one.

### 5. Submodule and dependencies
```bash
cd ~/ros2_ws_3/src/multi_franka_arm_ros2
git submodule update --init --recursive
cd ~/ros2_ws_3
rosdep install --from-paths src --ignore-src -r -s
```
What these do:
- **Submodule.** `mujoco_ros_pkgs` is a separate git repository placed inside ours, pinned to one
  exact commit that tenfoldpaper chose. A plain clone leaves the folder `mujoco_ros_pkgs/` empty.
  `git submodule update --init` downloads it at that pinned commit; `--recursive` also fetches any
  submodules it has itself.
- **rosdep.** Every ROS package lists what it needs in `<depend>` lines of its `package.xml`.
  rosdep reads those lines for all packages, translates each name into an Ubuntu package (for
  example `camera_info_manager` becomes `ros-humble-camera-info-manager`) and checks whether it is installed.
  - `--from-paths src`: look at every package under `src`.
  - `--ignore-src`: skip dependencies that are themselves packages in `src` (for example
    `mujoco_ros_msgs`, which the submodule provides and colcon builds).
  - `-r`: keep going when one name cannot be resolved, and report it at the end.
  - `-s`: simulate. Only print the `apt-get install` commands; change nothing.
  - rosdep needs ROS sourced (some `package.xml` lines depend on `$ROS_VERSION`); `~/.bashrc` already does that.

If rosdep complains that its database is missing or old, run `rosdep update` first (no sudo).
Daniel pastes the output; Opus checks the list. If packages are missing, Daniel runs the install
himself, because apt needs sudo: the same command without `-s`, or the `apt-get` lines it printed.

### 6. Build
```bash
cd ~/ros2_ws_3
MAKEFLAGS="-j4" colcon build --parallel-workers 2 --cmake-args -DCMAKE_BUILD_TYPE=Release
```
Limited to 2 packages at a time and 4 compile jobs each because of 7 GB RAM.
Check: the summary says all packages finished, no "failed".
