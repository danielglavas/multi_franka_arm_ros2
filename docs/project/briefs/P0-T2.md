## Steps

### 1. MuJoCo 3.2.0 into its own folder
Same recipe as the 3.1.6 build, with two changes:
- `-DCMAKE_INSTALL_PREFIX` sends the install to `~/Libraries/mujoco-3.2.0` instead of the default
  `/usr/local`, so 3.1.6 is not overwritten.
- `cmake --install .` instead of `sudo make install`. `/usr/local` belongs to root, which is why
  the old install needed sudo. A folder in Daniel's home belongs to him, so no sudo is needed.

The configure step downloads MuJoCo's third-party libraries. About 1 to 2 GB of disk, 10 to 20 minutes.
```bash
cd ~/za_libfranku
git clone https://github.com/google-deepmind/mujoco.git mujoco-3.2.0
cd mujoco-3.2.0
git checkout 3.2.0
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=$HOME/Libraries/mujoco-3.2.0 ..
cmake --build . -- -j4
cmake --install .
```
As with 3.1.6, this also builds and installs `simulate`, MuJoCo's own viewer program
(`~/Libraries/mujoco-3.2.0/bin/simulate`). Nothing else uses it; it is handy for opening a model by hand.

Check: `ls ~/Libraries/mujoco-3.2.0/lib/cmake/mujoco` lists `mujocoConfig.cmake`, and
`ls /usr/local/lib/libmujoco.so.*` still shows only 3.1.6.

### 2. Point `~/.bashrc` at MuJoCo 3.2.0
Replace lines 121-122 of `~/.bashrc` with the block below (it also removes the duplicate entries).
Daniel edits the file, or Claude does it with his OK at that time.
```bash
# MuJoCo 3.2.0 (own folder) comes first, so CMake and the loader find it before 3.1.6 in /usr/local.
export MUJOCO_DIR="$HOME/Libraries/mujoco-3.2.0"
export CMAKE_PREFIX_PATH="$MUJOCO_DIR:/opt/eigen-3.3.9/:/usr/local/lib/cmake/:$CMAKE_PREFIX_PATH"
export LD_LIBRARY_PATH="$MUJOCO_DIR/lib:/usr/local/lib/:$LD_LIBRARY_PATH"
export LIBRARY_PATH="$MUJOCO_DIR/lib:$LIBRARY_PATH"
```
Then open a new terminal (or `source ~/.bashrc`) before the next steps.

Effect on the old workspace: it still runs, because its programs ask for `libmujoco.so.3.1.6` by
name and that file stays in `/usr/local/lib`. Rebuilding it would pick up 3.2.0 and may fail.
Accepted: the new workspace becomes the main one.

### 3. Clone and add remotes
```bash
mkdir -p ~/ros2_ws_3/src && cd ~/ros2_ws_3/src
git clone https://github.com/danielglavas/multi_franka_arm_ros2.git
cd multi_franka_arm_ros2 && git checkout ultrasound
git remote add upstream https://github.com/tenfoldpaper/multipanda_ros2.git
git fetch upstream
git branch ultrasound-old-base ultrasound
```
What each line does:
- `mkdir -p ... && cd ...`: creates the workspace and its `src` folder, where colcon looks for
  packages. `-p` also creates the parent and does not fail if the folder exists.
- `git clone ...`: downloads our fork with its whole history into `multi_franka_arm_ros2`. Git names
  this remote `origin` and checks out the fork's default branch, `humble`.
- `git checkout ultrasound`: switches to `ultrasound`. Only `origin/ultrasound` exists after the
  clone, so git creates a local `ultrasound` that follows it. Its tip is the commit that added this brief.
- `git remote add upstream ...`: a named bookmark for tenfoldpaper's repo. Downloads nothing.
  It is called `upstream` so the CLAUDE.md rules ("never push to `upstream`", "`humble` mirrors
  `upstream/humble`") keep their meaning with the new base. The old `yilmazabdurrah` remote is not
  added; nothing in this project needs it any more.
- `git fetch upstream`: downloads tenfoldpaper's commits as `upstream/humble`. Our files and
  branches do not change.
- `git branch ultrasound-old-base ultrasound`: a second name for the current `ultrasound` commit,
  without switching to it. After the rebase moves `ultrasound`, this name still points at the old
  history, including the STL commit. Local only.

### 4. Move our commits onto the maintained repo
```bash
git rebase --onto upstream/humble 15be685 ultrasound
```
The three arguments:
- `ultrasound`: the branch to move.
- `15be685`: the cut point. Only commits made after it are taken: our 7 commits with docs,
  `CLAUDE.md`, `.claude/`, `.gitignore` and this brief (both versions). `15be685` itself (DAE to STL) and everything
  older stay behind. Its xacro edits point at files that have moved; P0-T4 redoes it and can reuse
  the STL files from `ultrasound-old-base`. (`15be685` sits directly on our old `humble`, `cf25b76`.)
- `--onto upstream/humble`: the new base. Git replays the 7 commits one by one on top of it.

The replayed commits get new commit IDs, so `origin/ultrasound` can later only be replaced with a
force-push (out of scope here).
If `.gitignore` conflicts, git stops in the middle: keep upstream's lines, add our line
`.claude/settings.local.json`, then `git add .gitignore && git rebase --continue`.
Check: `git log --oneline upstream/humble..ultrasound` lists our 7 commits, and
`git merge-base --is-ancestor upstream/humble ultrasound && echo ok` prints `ok`.

### 5. Submodule and dependencies
```bash
cd ~/ros2_ws_3/src/multi_franka_arm_ros2
git submodule update --init --recursive
cd ~/ros2_ws_3
rosdep install --from-paths src --ignore-src -r -s
```
What these do:
- **Submodule.** `mujoco_ros_pkgs` is a separate git repository placed inside ours, pinned to one
  exact commit that tenfoldpaper chose (`b3a65f3`). A plain clone leaves the folder
  `mujoco_ros_pkgs/` empty. `--init` registers the submodule from `.gitmodules`; `update` clones
  it and checks out the pinned commit; `--recursive` would also fetch its own submodules (it has none).
  This is tenfoldpaper's step "Install `mujoco_ros_pkg` (this fork)". Do not clone the fork
  separately as well.
- `cd ~/ros2_ws_3`: rosdep and colcon run from the workspace root.
- **rosdep.** Every ROS package lists what it needs in `<depend>` lines of its `package.xml`.
  rosdep reads those lines for all packages, translates each name into an Ubuntu package (for
  example `camera_info_manager` becomes `ros-humble-camera-info-manager`) and checks whether it is installed.
  - `--from-paths src`: look at every package under `src`.
  - `--ignore-src`: skip dependencies that are themselves packages in `src` (for example
    `mujoco_ros_msgs`, which the submodule provides and colcon builds).
  - `-r`: keep going when one name cannot be resolved, and report it at the end.
  - `-s`: simulate. Only print the `apt-get install` commands; change nothing.
  - rosdep needs ROS sourced (some `package.xml` lines depend on `$ROS_VERSION`); `~/.bashrc` already does that.

If rosdep complains that its database is missing or old, run `rosdep update` first (no sudo).
Daniel pastes the output; Opus checks the list. If packages are missing, Daniel runs the install
himself, because apt needs sudo: the same command without `-s`, or the `apt-get` lines it printed.

### 5.5. Test MuJoCo and mujoco_ros on their own
Builds only the MuJoCo packages and runs the fork's own test, so a MuJoCo problem shows up here
and not in the middle of the full build. Needs the dependencies from step 5.
```bash
cd ~/ros2_ws_3
MAKEFLAGS="-j4" colcon build --parallel-workers 2 --packages-up-to mujoco_ros2_control_system --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash
ros2 launch mujoco_ros2_control mujoco_ros2_control.launch.py
```
- `--packages-up-to mujoco_ros2_control_system`: build that package and everything it depends on, nothing else.
- The launch file starts MuJoCo with a test pendulum; no robot is involved.

Check: a MuJoCo window with a pendulum opens (fork README, step 7). Close it with Ctrl+C.

### 6. Build
```bash
cd ~/ros2_ws_3
MAKEFLAGS="-j4" colcon build --parallel-workers 2 --cmake-args -DCMAKE_BUILD_TYPE=Release
```
Limited to 2 packages at a time and 4 compile jobs each because of 7 GB RAM.
Check: the summary says all packages finished, no "failed".

### 6.5. Missing dependency: rosbridge_server
`franka_bringup/launch/sim/franka_sim.launch.py` includes `rosbridge_server`'s launch file, but
`franka_bringup/package.xml` does not declare it, so rosdep in step 5 does not list it. Without it the
launch stops at once with `PackageNotFoundError: "package 'rosbridge_server' not found"`.
Daniel installs it (10 apt packages, nothing removed):
```bash
sudo apt-get install ros-humble-rosbridge-server
```
rosbridge opens a WebSocket server on port 9090 that lets programs outside ROS read and send ROS
topics. Harmless in simulation; worth remembering for the real robot, since anything on the network
that reaches the port can send ROS messages.
